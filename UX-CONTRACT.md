# Inventory TI UX Contract

This contract records frontend interaction ownership. Product rules, permissions, and lifecycle constraints remain owned by the API and the technical/product documentation.

Shared behavior below is the required interaction contract, not proof that every consumer already complies. Current differences are listed under Known contract gaps and in the [API reconciliation](docs/technical/frontend.md#8-api-contract-reconciliation); documenting them does not waive the requirements.

## Shared behavior

- `Select` is authored. Small fixed option sets use its simple variant; large entity sets use the same component with local search. Searchable popups render eight matches by default, keep the current selection reachable, and disclose when more matches require refining the query. Search operates on supplied options, not an independent server query. It owns focus, Arrow keys, Enter, Escape, visible selection, bounded scrolling and popup positioning. A popup opened during a dialog's entrance animation remeasures its anchor when that animation finishes, so its width and position do not retain the dialog's temporary scale.
- Active/inactive state is represented with the shared `Switch`. The feature owns the server mutation and any confirmation required by the operation.
- Dialogs stay fixed and centered in the viewport regardless of the page's scroll position, preserve focus, close through Escape when not busy, restore trigger focus without scrolling the underlying list, keep long content internally scrollable, and respect reduced motion. Initial focus must not move the page; cleanup also restores focus for conditionally unmounted history/detail dialogs. Opening or closing a read-only dialog preserves loaded rows and filters.
- Remote list search is debounced for 300 ms, keeps a visible clear control, and ignores stale responses through feature request IDs. Search labels identify only their input; clearing restores input focus without scrolling the list.
- Loading uses stable button geometry and table skeletons; empty and request errors use shared feedback components.
- Feature routes load on demand. Their shared loading state and localized error/reload fallback stay inside the content area, leaving navigation and theme controls usable. Route transitions keep their existing direction and reduced-motion behavior.
- Dashboard and Corrections use the same date picker, including its month/year controls and opening/closing animation. Selecting a month or year closes only that select, not the calendar; optional empty dates display “Seleccionar fecha”.
- Inventory movement dialogs reuse that DatePicker's named inline variant: the expanded calendar participates in the internally scrolling body instead of being clipped by it. Header/actions stay reachable. Date errors have instance-specific associations; month/year selects have localized accessible names.
- The Corrections filter drawer owns a positioned stacking context above its results, so an open calendar remains readable and clickable over loading, empty, and populated tables. Its height follows the inner content on viewport changes; absolute popups do not enlarge the drawer.
- Toasts use the single root provider and fixed top-right placement. Identical messages within two seconds replace each other; at most four remain visible. Success, information and warning messages close after five seconds, while errors persist until dismissed. When an actionable mutation fails inside a dialog, the localized recovery message appears inline in that dialog and is echoed through the shared error toast so it remains visible without hiding the form context.
- Auto-dismiss pauses during pointer hover or keyboard focus. Refreshing an identical toast cancels any pending exit timer and restarts its lifetime. Toasts acknowledge server-confirmed outcomes; validation and actionable request failures remain inline, and raw backend errors never become toast copy.
- All feature requests use `apps/web/src/lib/api.ts`. Error codes and HTTP/network failures are translated by `getApiErrorMessage`; modal request handlers use the shared `useRequestError` hook to return that same message for the inline alert and publish a persistent error toast. List loading errors stay visible in their page/table. A failed history load is an error state with retry, never an empty history.
- Failed incremental requests preserve the loaded rows and pause automatic loading until an explicit retry or filter change. Page loading failures expose retry and do not masquerade as empty datasets; a failed dashboard refresh never renders unconfirmed zero metrics or empty charts. Confirmations stay open after a failed mutation.
- Toasts join the browser top layer through a manual popover, hosted inside the active native dialog when one is open. This keeps the notification visible and its dismiss control reachable while the rest of the document is inert. When a mutation closes or unmounts that dialog, the provider resolves a connected host before opening the popover; the notification moves to the remaining dialog or page without being lost or crashing the application. Network failures describe an unconfirmed result and recommend refreshing before repeating a stock-changing operation.
- Theme preference is stored locally as `light`, `dark`, or `system`. System mode follows `prefers-color-scheme` changes without overriding an explicit user choice.
- Shared feedback preserves semantic color roles in every theme: brand yellow for identity/action/active/highlight, blue for information, green for success, orange for warning and red/rose for danger. Solid brand yellow always uses black text.
- Shared controls expose a visible blue focus indicator, a consistent disabled treatment and token-owned surfaces. Surface, dropdown and dialog are the only shared elevation roles.
- Primary navigation stays in the full-width top header on desktop and becomes a fixed, equal-width, icon-only bottom bar below 1024px. Each link keeps its Spanish accessible name and native title tooltip. It respects safe-area insets and the content shell reserves clearance so navigation never covers page actions.
- Responsive rows preserve the full identity, status, permissions, actions and dataset navigation. `mobileRole` explicitly defines card structure; the first or last desktop column does not implicitly become its header/footer. Inventory's native tables use the same `data-card-role` contract. Long values wrap without hiding information or forcing lateral scrolling. Corrections retain original/result values in their adjustment context when the equivalent standalone columns are hidden. Cards use document scrolling and shared responsive loading/empty feedback.
- When a table value is visually clipped, the shared `OverflowText` owner exposes its complete value on hover and keyboard focus. Responsive cards wrap the same text in place, so touch users can read it without relying on a hover tooltip.

## Authentication behavior

Authentication uses the shared theme preference and an in-flow brand/theme header in both sign-in and activation. Narrow screens show the sign-in form without the desktop story panel; document scrolling keeps fields, errors and submit reachable on short screens. Login uses shared button and localized form-error feedback, owned validation, password-manager autocomplete and an accessible show/hide control. Busy submission preserves button dimensions and blocks duplicate requests. Invalid credentials should preserve the identifier and clear the password; the current LoginPage retains the password, a known gap rather than verified compliance. Sign-in and activation set localized document titles and restore the previous title when leaving.

Account creation/reset delivers a one-use code with a 24-hour lifetime. Administrative activation controls `isActive`, while password activation controls `isActivated`; reset does not reactivate an inactive account, and successful password activation does not create a session. Activation should be reachable directly by somebody with a code: currently its button only appears after an `ACCOUNT_PENDING` login response, although the login form requires a password.

## User administration behavior

- The Users toolbar always exposes “Nuevo usuario” to `JEFE`, including when the list contains records or has active filters. It uses the shared `PageToolbar` action slot and the existing user editor, matching Catalog's create entry point.
- Creation collects the name, unique username, email, phone and role. A successful request closes the editor, refreshes the current list and opens the activation-code dialog; the person configures their own password during activation. Existing filters remain applied, so a new account may not match the current view.
- Failed creation keeps the editor and its values open with localized inline and toast feedback. Busy submission blocks repeat submits. Backend authorization and CSRF remain owned by `POST /users` in `apps/api/src/auth/routes.ts`; only `JEFE` may create accounts.
- Administrative access reset is unavailable for the connected account; the API rejects it before invalidating credentials or sessions. Own password changes use Mi cuenta. User search is debounced and cancels superseded requests; stale responses never replace the active query.
- The backend's [last-administrator safeguard](docs/product/roles.md) can reject deactivation, role changes or access reset with `LAST_ADMIN_REQUIRED`. The shared API translator explains in Spanish that another active Jefe must configure a password first; existing dialogs preserve their values and display the same inline and persistent-toast error. A pending account never counts as a replacement administrator.

## Dashboard data and date filters

- Dates affect movement charts, not current product/stock/asset/alert KPIs or pending corrections. Recalculation animation does not imply historical snapshot support. The default is the first day of the current Chile month through today.
- Dashboard is a consultation view over existing REST reads. Its current availability to every authenticated role conflicts with the product matrix denying SOPORTE access; [this decision remains open](docs/technical/frontend.md#unresolved-dashboard-access-policy). Documentation does not grant a new permission.
- Dashboard and Inventory read every product page required by the current API contract; rendering remains incremental. Pending correction counts and detail lists include every pending page, not just the first response.
- Date-only filters in Dashboard and Corrections use explicit America/Santiago day boundaries converted to UTC, including daylight-saving changes. Defaults also use the Chile calendar day rather than slicing a UTC timestamp.
- Movement totals cover the entire selected period. The trend uses daily, weekly or monthly buckets according to its length, without discarding older movements or interpreting negative exits as negative volumes.
- Charts consume immutable `/inventory/movements` quantities. Approved compensations contribute to adjustment volume on their recorded dates; charts do not substitute corrected effective quantities into past entry/exit bars. Corrected running history is a different view.
- Corrections keep the next server offset independent from referenced rows injected by a deep link and reconcile subsequent pages by record ID. The retained table search makes the record reachable after closing its detail; it does not add a distinct selected-row highlight. Mobile cards show original, final and delta values through their adjustment context.

## Dataset loading contract

| View | Fetching | Incremental presentation |
| --- | --- | --- |
| Catalog / Users | Server pages of 25. | Scroll-triggered next page plus load-more/retry controls. |
| Corrections | Server pages of 25. | Scroll-event next page; explicit next-page control is still missing. Page retry restarts the first page. |
| Inventory quantity / assets | Full reads, including all required product pages. | Local filtering and blocks of 25 per tab. |
| Quantity history | Complete corrected response, chronologically ordered. | Blocks of 12; compensation disclosure has its own block of 12. |
| Asset history | Complete received timeline, newest first; server caps each of its three source reads at 200 rows. | Blocks of 12 do not retrieve additional historical source pages. |
| Dashboard pending-correction modal | All pending pages. | Button reveals 25 at a time. |
| Dashboard asset/attention modals | Matching snapshot records. | Full matching list, no server page control. |
| Assignment modal | Server pages of 25, newest first; currentAssignment is independent of list pages. | Load-more/retry preserves prior rows and drafts; offset advances by received records rather than deduplicated DOM rows. |

Incremental DOM rendering must not be described as server pagination when the response was already fetched in full. Opening a read-only modal preserves the underlying list state. Current data is REST-based, not automatically synchronized through WebSocket.

## Personal account behavior

- Mi cuenta separates personal identity/contact from editing controls. Edit opens inline fields without sending a mutation; only explicit Save submits. Cancel discards the draft.
- Name, email and phone are editable personal data. Username is unique and read-only here; role changes remain JEFE-only through Users. Phone display is formatted while submission is normalized.
- Password change uses the shared dialog and requires the current password plus a new password of 12–128 characters, including an ASCII letter and digit; the API enforces the full range. Confirmation follows the server response; failure preserves context with localized inline/toast feedback. `INVALID_CURRENT_PASSWORD` must not trigger the global expired-session event.

## Inventory asset status behavior

- Inventory separates operational assets, decommissioned archive and all assets using coherent API queries. Archive rows retain read-only history but never ordinary editing, assignment or status actions. Dashboard counts exclude inactive/decommissioned assets.
- Quantity movements accept optional reference and an explicit Chile date plus typed HH:MM. Both date/time are required together and converted with America/Santiago, including seasonal offsets. Nonexistent or ambiguous daylight-saving times require correction, not an invented time. Leaving both empty omits effectiveAt and retains the server default.
- Metadata and availability V1 are deployment-gated by VITE_INVENTORY_METADATA_V1=true (false by default). Enable only after the API/schema deployment documented in docs/planning/excel-mda/contrato-api-v1.md. Catalog/asset forms preserve optional/null semantics; asset metadata edits send only changed fields. Condition, purpose and descriptive location never imply an operational state.
- The V1 availability tab uses real server pages of 25 with load-more/retry, preserving received rows after a page error. Dashboard ASSET alerts use backend lowStock and availableCount, never total assets or assigned counts. Period filters still affect movements only.

- “Cambiar estado” appears in each active, unassigned asset's action dock and responsive record card. It uses the shared `Dialog`, `Field`, `Select`, `Button`, existing status badges and toast provider; the current and proposed states remain visible before submission.
- State options follow `changeAssetStatus` in `apps/api/src/routes/assets-service.ts`: support may select available, reserved, under review or in repair; jefe/coordinador may also select in warranty or lost. The current state, assigned and decommissioned are never selectable. Assigned assets must use the existing return workflow first; decommissioned/inactive assets have no operational-state action.
- The selection starts empty. Saving requires an allowed destination, blocks duplicate requests, and sends `POST /assets/:id/status` with CSRF protection. Failure keeps the selection and dialog open with Spanish inline and toast feedback.
- Only the server-confirmed asset replaces its row. Search, active filters, loaded record counts and the list's scroll remain intact; an asset that no longer matches the active state filter disappears from that filtered list. The modal completes its shared exit animation before unmounting. The existing history endpoint supplies the audit event, including actor, date and previous/new state; frontend code never invents a successful history entry.

## Inventory deliveries and returns

The [V2 API contract](docs/planning/excel-mda/contrato-api-v2.md) owns destinations, roles, date constraints and return state. The existing integrated Inventory entry point uses AssetAssignmentDialog with the canonical Dialog/Field/Select/DatePicker/feedback owners, not a new visual system.

- Deployment flag VITE_INVENTORY_ASSIGNMENTS_V2=true is false by default. Enable after the documented API/Prisma/migrations deployment; disabling keeps personName-only delivery and body-less return requests.
- Person and office are distinct destinations. Switching preserves local drafts but sends only the selected destination. Standard delivery is not labeled permanent; Loan is an explicit delivery type, separate from the asset's loanCode.
- Expected return is optional and may be future. Only its calendar opts into allowFuture; this does not promise automatic overdue monitoring or notifications.
- Manual effective dates are shown only to Jefe/Coordinador and converted from a complete Chile date/time pair. Support may set a loan forecast but never sends explicit effectiveAt. Server capture and effective time remain distinct; unknown old capture/status values are not invented.
- Return has its own incoming ticket/OT/notes and the API-approved destination state. Only a confirmed Available result permits another delivery; Under review / In repair remain unavailable until the existing state workflow makes them available.
- Read-only delivery history is reachable for non-available and archived assets without exposing ordinary assignment/return actions.
- Initial/history-page errors have explicit retry. Incremental failure retains rows and draft; retry targets the failed offset. Refreshing preserves the form for the same assignment, but a changed active assignment id exits the previous return flow rather than applying its draft to another delivery.
- Busy and uncertain outcomes block duplicate writes. Network or invalid-response uncertainty keeps the draft visible and requires refreshing currentAssignment before another attempt; refresh is a read, never an automatic POST retry.
- Close completes the shared exit animation. Read-only close preserves the list; after mutation refresh, focus returns to the surviving action of the same asset or the list search without scrolling.

## Import review behavior

The V4 review entry point belongs to features/imports/ImportReviewPage.tsx and the existing Inventory command band. VITE_INVENTORY_IMPORT_REVIEW_V4=true is false by default and requires the API/schema deployment documented in docs/planning/excel-mda/contrato-api-v4.md. Only JEFE can enter; disabled/forbidden states issue no import requests. Backend remains the authorization authority.

- Reuse the Catalog full-width surface, shared headers/filters, semantic responsive tables, Dialog, Field, Select, badges and feedback. No new dashboard, UI kit or extra mobile navigation destination.
- This screen reads existing administrative batches and the original saved V3 snapshot. It does not upload XLSX or create batches. Counts describe analysis, never confirmed stock. The independently gated pilot workflow below adds planning and explicit application, not a general importer.
- Physical observations/history are reviewed by backend-grouped candidate; consumables/manual summaries/notes by source record. Keep sheet/row/hidden-row provenance and literal original cells available. Formula/cache values are evidence only and never executed or treated as verified results.
- Lotes and decision history use real server pages of 25; failed pages preserve received rows and drafts, and retries retain their offset. Snapshot tables and evidence use local blocks of 25. Batch/content/sheet filters are in the URL; list pages remain in memory while reviewing a target.
- Current decision is read independently of event history. Every write needs an explicit reason, captures batch version and a stable request UUID, and sends only a permitted action/suggested link. Propose/link decisions do not change real inventory. Coverage complete does not mean approval or resolved issues.
- Server freshness controls eligibility. Inventory/rule drift blocks link/new proposals, but allows pending/exclude. A date-only change is a separate warning.
- Version conflict preserves draft and requires explicit refresh, never silently overwriting expectedVersion. Unknown write outcomes freeze the captured intent; recovery resends that exact idempotency key/body. After confirmation re-read current decision before presenting it as current.
- Initial errors are not empty datasets. Dirty/uncertain modal closure requires an inline choice; the least destructive control receives focus. Shared exit animation restores trigger focus. beforeunload warns on document exit; declarative-router Back navigation is not draft-blocked. No private workbook evidence is persisted to browser storage.

## Import source and identity revision

The backend [V7 source contract](docs/planning/excel-mda/contrato-api-v7.md) and [V8 identity contract](docs/planning/excel-mda/contrato-api-v8.md) own field mapping, candidate grouping, provenance, conflicts and reapproval. SourceReviewPanel/SourceRevisionDialog reuse Catalog's Dialog, Field, authored Select and semantic table owners; no new design system or operational CRUD fallback.

- VITE_INVENTORY_IMPORT_SOURCE_V7 and VITE_INVENTORY_IMPORT_IDENTITY_V8 are independently false by default and require JEFE/V4. Deploy the current source-aware backend and prerequisite schema (including 0017/0018) before enabling. This work neither enables deployment flags nor migrates a database.
- Descriptive review selects a physical candidate and mapped row, then queues 1–25 unique field changes. Type/brand/model and reception date are the only descriptive fields; mapping comes from preview keys, never guessed Excel columns. Historical reception dates use a labeled ISO text-entry variant (AAAA-MM-DD, from 1900, no future date), not the shared calendar's narrower 2020 range.
- Identity verification applies to the whole original candidate (at most twelve observations), not an isolated row. Serial and tag are text with preserved leading zeros; each is explicitly verified or explicitly absent. Server authority prevents dropping populated/uncertain evidence, merging/splitting candidates and overlapping identities. Human confirmation, reason and evidence reference are required.
- Restore queues original descriptive cells or restores the complete original identity. Show its scope and possible reintroduced blockers before saving. No history is erased; formulas remain literal and are never executed. Original saved evidence and current interpreted cells are explicitly separate.
- Save captures both batch version and source revision with an immutable UUID/body and CSRF. Double submit is synchronously blocked; conflicts retain draft and require explicit refresh. Source reads and the CSRF/write sequence have a 30-second transport deadline. An expired/unknown write freezes its intent for explicit recovery with the same UUID/body; aborting transport never claims a server rollback.
- Confirmed revisions show a historical proof, then read the current head; an older idempotent reply never replaces the current source. Histories load real descending server pages of 25, retain rows on page failure and retry the failed offset. A changed head while paging requires refreshing the complete list to avoid offset skips.
- With either source gate enabled, every review action (including pending/excluded) captures expectedSourceRevision and uses the effective target while retaining its original ID. Latest decision/source/batch reads must agree before saving. Verification AND restoration of identity require a new explicit decision; prior history never implies reapproval.
- Close/Escape, switching a candidate with a draft, and document exit disclose draft loss; continuing preserves inputs. Values and recovery intents stay in modal memory, never localStorage. Internal Back remains unguarded by the declarative BrowserRouter, as in the existing review flow.
